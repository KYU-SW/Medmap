나는 의료IT공학과 3학년 학생이고, 지금부터 **MedMap이라는 의료IT 캡스톤 디자인 프로젝트를 실제로 개발·연구하기 시작하려고 한다.**

아래 내용은 이전 ChatGPT와 장기간 논의하면서 결정한 **현재 최종 프로젝트 방향과 연구 설계**다.
새로운 아이디어를 처음부터 제안하는 것이 아니라, **아래 내용을 프로젝트 기준안으로 숙지한 뒤 실제 구현과 실험을 단계별로 진행해줘.**

# 1. 프로젝트 이름

**MedMap**

핵심 개념:

> **환자의 증상과 시간에 따른 변화를 축적하고, 진료 전·중·후의 정보를 연결하여 현재의 진단이 환자의 상태를 충분히 설명하고 있는지 확인하도록 돕는 ‘진단 안전망(Diagnostic Safety Net)’**

MedMap은 의사를 대신해서 진단하는 AI가 아니다.

핵심은:

**“무슨 병인지 맞히는 AI”가 아니라
“현재 내려진 진단과 환자의 실제 정보 사이에 중요한 불일치가 있는지 찾아서 다시 확인할 시점을 알려주는 시스템”**

이다.

---

# 2. 최종 핵심 기능

전체 제품 방향은 다음과 같다.

**환자 증상 기록**
→ **임상정보 구조화**
→ **Patient Map / 증상 타임라인 생성**
→ **질환 후보 탐색**
→ **현재 진단과 환자 정보의 불일치 탐지**
→ **필요한 경우 대안 질환 탐색**
→ **Next Best Information 제안**
→ **의사의 최종 판단**

진료 전·중·후로 나누면:

### 진료 전

* 환자가 음성 또는 텍스트로 증상 입력
* 증상, 과거력, 복용약, 알레르기, 시간 정보 등을 구조화
* 일상적인 표현을 의학용어로 정규화
* 증상의 발생 시점과 변화 과정을 타임라인으로 정리
* 환자가 직접 확인·수정
* 의사에게 전달할 수 있는 문진 요약 생성

### 진료 중

의사의 **working diagnosis(현재 잠정 진단)**와 환자의 실제 정보가 잘 맞는지 확인한다.

핵심 질문:

> **“현재 진단으로 환자의 중요한 소견들을 충분히 설명할 수 있는가?”**

* 문제가 없으면 경고하지 않는다.
* 중요한 불일치가 있을 때만 경고한다.
* 현재 진단과 잘 맞지 않는 소견을 표시한다.
* 대안 질환을 1~3개 정도 탐색한다.
* 현재 진단과 대안 질환을 구별하는 데 가장 유용한 추가정보를 **Next Best Information**으로 제안한다.

### 진료 후

* 의사의 진단
* 처방
* 주의사항
* 재진 조건
* 예상 회복 과정

등을 저장한다.

이후 환자가 기록하는 실제 증상 변화와 예상 회복 과정을 비교하여 **예상과 다른 경과가 나타나는지** 확인하는 방향을 장기적으로 고려한다.

# 3. 가장 중요한 연구 문제

이번 캡스톤의 1차 연구에서 가장 중요한 질문은 두 가지다.

### 연구 질문 1

> **부분적으로 관찰된 환자 정보로 만들어진 working diagnosis가 잘못되었는지를 독립적인 의료지식으로 탐지할 수 있는가?**

### 연구 질문 2

> **진단 불일치 경고 이후 추가정보 1~3개를 확인했을 때 실제 정답 진단을 얼마나 회복할 수 있는가?**

따라서 단순한 질환 분류 정확도만 측정하는 프로젝트가 아니다.

핵심 평가 대상은:

**잘못된 진단을 찾아내는 능력 + 정상적인 진단에 불필요한 경고를 하지 않는 능력 + 추가정보를 통해 올바른 진단으로 회복하는 능력**

이다.

---

# 4. 반드시 유지해야 하는 핵심 설계 원칙

## ① 증상 구조화와 질환 추론을 분리한다

두 문제를 하나의 AI로 섞지 않는다.

### 문제 A — 대화 이해·증상 구조화

입력:

> “어제부터 머리가 아프고 열은 없어요.”

출력:

* 증상: 두통
* 발생 시점: 어제
* 발열: 없음
* 통증 강도: 확인되지 않음

단순히

> “머리가 아파요 → 두통”

으로 바꾸는 것이 아니다.

다음 정보를 보존해야 한다.

* 부정 표현
* 발생 시점
* 지속 시간
* 중증도
* 증상 변화
* 과거력
* 약물
* 원문 근거

또한:

**“없음”과 “확인되지 않음”을 반드시 구분한다.**

---

## 문제 B — 질환 후보 추론

구조화된 증상과 환자 배경을 기반으로 질환 후보를 탐색한다.

원칙:

* 하나의 질환으로 단정하지 않는다.
* 정보가 부족하면 추가 질문한다.
* 판단할 수 없으면 판단을 보류할 수 있어야 한다.
* LLM이 생성한 점수나 순위를 실제 발병확률처럼 표현하지 않는다.

# 5. MedMap의 핵심 연구 구조

이번 1차 연구에서는 다음 구조를 사용한다.

### Step 1. DDXPlus 환자 정보 준비

DDXPlus의 환자 정보를 사용한다.

### Step 2. 일부 정보만 관찰

실제 진료처럼 처음부터 모든 환자 정보를 제공하지 않는다.

예:

전체 환자 정보가 10개라면

처음에는 3~5개만 제공

→ **부분 관찰(partially observed) 환경**

을 만든다.

### Step 3. 기본 진단 모델

부분적으로 관찰된 정보만 보고 기본 진단 모델이 현재 가장 가능성이 높은 질환을 선택한다.

이것을:

**working diagnosis**

로 정의한다.

### Step 4. 정답과 비교

working diagnosis가 DDXPlus의 실제 정답과 같으면:

**correct working diagnosis**

다르면:

**incorrect working diagnosis**

로 구분한다.

중요:

잘못된 working diagnosis가 자연스럽게 생성되어야 한다.

단순히 일부러 틀린 답을 집어넣는 실험으로 만들지 않는다.

### Step 5. 불일치 탐지

MedMap이 현재 working diagnosis와 환자의 전체/추가 정보 사이에서 중요한 불일치를 찾아낸다.

개념적으로:

> 현재 진단에서는 잘 설명되지 않는 소견이 존재하는가?

를 판단한다.

예:

현재 진단 = 질환 A

환자에게 관찰된 소견 = f

그런데 f가 질환 A에서는 드물고 다른 질환 B에서는 흔하다면:

→ 진단 불일치 점수 증가

### Step 6. 경고 여부 판단

불일치가 작으면 경고하지 않는다.

불일치가 충분히 크면:

> “현재 진단으로 설명하기 어려운 소견이 있어 재검토가 필요합니다.”

와 같은 경고를 제공한다.

### Step 7. 대안 질환

필요한 경우 대안 질환을 1~3개 제안한다.

단순히 가장 가능성이 높은 질환을 다시 출력하는 것이 아니라:

**현재 working diagnosis를 위협할 수 있는 대안**

을 찾는 것이 중요하다.

### Step 8. Next Best Information

현재 진단과 대안 질환을 가장 잘 구별할 수 있는 추가정보를 제안한다.

추가정보는:

* 추가 문진
* 과거 의료기록
* 신체검사
* 기존 검사 결과
* 새로운 검사

등이 될 수 있다.

예:

> “두 질환을 구별하기 위해 최근 발열 여부를 확인하는 것이 중요합니다.”

처럼 **진단을 구별하는 정보**를 제안한다.

---

# 6. Next Best Information의 원칙

NBInfo는 무조건 질문을 많이 하는 기능이 아니다.

### 진료 전

부족한 기본 환자정보를 채우는 데 사용.

### 진료 중

현재 진단과 대안 질환을 가장 잘 구별하는 정보를 선택.

특히:

> **“이 정보를 알게 되면 현재 진단과 대안 중 무엇이 더 타당한지 판단하는 데 얼마나 도움이 되는가?”**

가 중요하다.

희귀질환 검색도 무조건 하지 않는다.

다음 조건에서만 확대한다.

* 현재 진단과 중요한 불일치가 있음
* 흔한 대안으로 충분히 설명되지 않음
* 특이적인 특징 조합이 존재함

# 7. 1차 연구 범위

현재 가장 중요한 연구는 이것이다.

**DDXPlus**
→ 부분 관찰 환자 생성
→ 기본 진단 모델
→ working diagnosis 생성
→ correct / incorrect 구분
→ 진단-소견 불일치 점수
→ 잘못된 진단 탐지
→ 오경보 검증
→ 외부 독립 의료지식 연결
→ Next Best Information
→ 추가정보 1개 / 3개 후 정답 회복률 평가

### 1차 연구에서 제외

아래 기능은 제품 아이디어로는 유지하지만 **1차 연구 범위에서는 제외한다.**

* 한국어 STT/NLP 전체 구현
* 실제 EMR 연동
* 실제 QR 연동
* 응급도 예측 모델
* 의료기관 추천 모델
* 장기간 실제 환자 경과 연구
* 실제 임상에서 오진 감소를 입증하는 연구

# 8. 데이터셋 — DDXPlus

현재 가장 먼저 사용할 데이터셋.

공식 GitHub:

https://github.com/mila-iqia/ddxplus

DDXPlus는 합성 환자 데이터셋이며:

* 증상/소견
* 환자 정보
* 질환
* 감별진단 후보

등을 포함한다.

중요:

**DDXPlus는 합성 데이터이므로 실제 환자 대상 성능으로 해석하지 않는다.**

우리 연구에서는:

> **부분적으로 관찰된 환자 정보에서 working diagnosis가 만들어지고, 그 진단이 잘못되었을 때 이를 탐지하는 실험 환경**

을 만드는 데 사용한다.

# 9. DDXPlus 다운로드 후 가장 먼저 할 일

프로젝트 시작 시 바로 다음을 확인한다.

1. train / validate / test 구조
2. 환자 데이터 컬럼
3. 질환 label
4. evidence / symptom 구조
5. differential diagnosis 정보
6. 각 질환별 evidence 관계
7. 데이터 개수
8. 질환 개수
9. 증상/소견 개수
10. missing / unknown 표현 방식
11. train/validation/test leakage 가능성

그리고 실제 데이터를 직접 읽어서:

* dataframe shape
* 컬럼명
* sample
* label 분포
* evidence 구조

를 확인한다.

**데이터를 직접 확인하기 전에 임의로 데이터 구조를 가정하지 않는다.**

---

# 10. 외부 의료지식 — 매우 중요

DDXPlus 자체에서 얻은 질환-소견 관계만 사용하면 순환논리가 생길 수 있다.

따라서 핵심 실험에서는 DDXPlus와 독립적인 외부 의료지식을 사용한다.

검토 대상:

* HPO
* UMLS
* SNOMED CT
* OptimusKG
* Orphadata / Orphanet 등

목적:

**DDXPlus의 정답을 그대로 다시 사용하는 것이 아니라 독립적인 의료지식으로 현재 진단과 환자 소견 사이의 불일치를 탐지할 수 있는지 확인**

한다.

# 13. MIMIC 관련 진행상황

MIMIC 계열 데이터는 현재 1차 연구의 즉시 시작 데이터가 아니다.

PhysioNet 접근에는 일반적으로:

* Credentialed Access
* CITI 교육
* Data Use Agreement

등의 조건이 있다.

이전에 PhysioNet Credentialed Access 신청을 진행했고, CITI 교육도 진행했던 것으로 기억하지만 **완료·승인·DUA 서명까지 모두 완료됐다고 가정하지 않는다.**

현재 실제 상태가 필요하면 PhysioNet 계정에서 직접 확인한다.

Credentialing:

https://physionet.org/settings/credentialing/

CITI 안내:

https://physionet.org/about/citi-course/

# 14. 응급도/의료기관 추천 기능

이 기능은 과거에 별도로 검토했던 확장 기능이다.

구조:

**증상 + 활력징후**
→ **응급도 예측**
→ **의료기관 수준 안내**

MIMIC-IV-ED를 후보 데이터셋으로 검토했다.

https://physionet.org/content/mimic-iv-ed/2.2/

MIMIC-IV-ED에서 검토한 입력:

* chiefcomplaint
* temperature
* heartrate
* resprate
* o2sat
* sbp
* dbp
* pain

라벨 후보:

**acuity**

acuity는 ESI(Emergency Severity Index) 1~5 단계 응급도.

* 1에 가까울수록 높은 응급도
* 5에 가까울수록 낮은 응급도

하지만:

**ESI = 병원 등급이 아니다.**

따라서

`ESI 1 → 상급종합병원`

같은 식으로 직접 변환하면 안 된다.

의료기관 추천은 별도의 문제다.

또한 MIMIC-IV-ED의 실제 `disposition`이나 MIMIC-IV-Ext CDS의 referral/triage/diagnosis 관련 데이터도 검토했지만, **이 기능은 현재 1차 연구에서 제외한다.**

나중에 확장 연구/제품 기능으로 다시 검토한다.

---

# 15. 과거 의료정보가 MedMap에서 중요한 이유

MedMap에서는 환자의 다음 정보를 장기적으로 저장하는 것을 고려한다.

* 복용약
* 알레르기
* 과거 질환
* 수술력
* 가족력
* 과거 검사 결과
* 활력징후
* 증상 변화

이 정보는 단순한 저장 기능이 아니다.

새로운 증상이 발생했을 때:

**현재 증상**
+
**관련된 과거 의료정보**

를 연결하여 현재 진단을 평가하는 데 사용한다.

예:

현재:

> 어지럼증 + 검은 변

과거:

> 항응고제 복용
> Hb 지속 감소
> 위궤양 병력

→ 과거 의료정보가 현재 증상 해석에 중요한 맥락이 될 수 있음.

하지만 모든 과거정보를 무조건 모델에 넣는 것이 아니라:

**현재 증상 → 관련 과거 의료정보 검색 → 관련 정보만 추론에 사용**

하는 방향을 고려한다.

---

# 16. Patient Map

MedMap의 제품적 핵심 중 하나.

환자의 의료정보를 시간축으로 연결한다.

예:

```text
과거 질환
   ↓
복용약
   ↓
검사 결과 변화
   ↓
새로운 증상
   ↓
현재 진단
   ↓
추가 검사
   ↓
치료
   ↓
회복/악화
```

단순한 의료기록 저장소가 아니라:

> **“현재 문제와 과거의 어떤 정보가 연결되는가?”**

를 보여주는 구조다.

---

# 17. 주요 평가 지표

1차 연구에서 반드시 고려할 지표:

### 잘못된 진단 탐지율

실제로 틀린 working diagnosis를 얼마나 잘 잡아내는가.

### 오경보율

올바른 working diagnosis인데도 괜히 경고하는 비율.

**낮은 오경보율이 중요하다.**

### AUROC

진단 불일치 탐지 성능 평가.

### AUPRC

불균형 데이터에서 보조적으로 평가.

### 낮은 오경보율 조건에서의 탐지율

실제 시스템에서 중요한 지표.

### 추가정보 1개 후 정답 회복률

NBInfo 1개를 추가했을 때 정답 진단으로 얼마나 회복되는지.

### 추가정보 3개 후 정답 회복률

NBInfo 최대 3개를 추가했을 때 얼마나 회복되는지.

# 21. 매우 중요한 주의사항

앞으로 프로젝트를 진행할 때 다음 원칙을 반드시 지켜줘.

1. **실제 데이터와 합성 데이터를 구분할 것.**
2. DDXPlus의 성능을 실제 환자 대상 성능처럼 표현하지 말 것.
3. 의료 데이터셋의 다운로드 가능 여부, 승인 조건, 비용, 라이선스는 가능하면 공식 출처로 확인할 것.
4. 데이터 구조를 추측하지 말고 실제 파일을 확인할 것.
5. 논문/캡스톤에서 주장하는 내용과 단순 제품 아이디어를 구분할 것.
6. DDXPlus 정답을 이용해서 다시 DDXPlus 정답을 맞히는 순환논리를 피할 것.
7. 외부 의료지식을 사용할 때 DDXPlus와 독립적인지 확인할 것.
8. LLM이 만든 확률/점수를 검증된 임상 확률처럼 표현하지 말 것.
9. AI가 의사의 진단을 대체한다고 표현하지 말 것.
10. “현재 진단이 틀렸다”고 단정하는 것이 아니라 **“현재 정보와 진단 사이에 중요한 불일치가 있어 재검토가 필요하다”**는 구조로 설계할 것.
11. 불일치가 작을 때 무조건 경고하지 말 것.
12. Next Best Information은 단순히 질문을 많이 생성하는 기능이 아니라 **현재 진단과 대안을 구별하는 데 정보 가치가 높은 항목을 선택하는 기능**으로 설계할 것.
13. 희귀질환 검색은 무조건 실행하지 않고 필요한 조건에서 확대할 것.
14. 한국어 STT/NLP, MIMIC, 실제 EMR 연동 등 아직 구현하지 않은 기능을 이미 구현된 것처럼 말하지 말 것.
15. 캡스톤 수준에서 실제 구현 가능한 범위를 우선한다.
16. 기능을 계속 추가해서 프로젝트 범위를 무작정 키우지 않는다.
17. **현재 최우선 목표는 DDXPlus를 실제로 분석하고 1차 실험을 시작하는 것**이다.

# 22. 지금 바로 해야 할 일

이 프롬프트를 읽었다면 프로젝트 설명을 다시 길게 반복하지 말고 바로 작업을 시작해줘.

**첫 번째 작업은 DDXPlus 데이터 구조 분석이다.**

다음 순서로 진행해줘.

1. DDXPlus 공식 데이터 다운로드 경로 확인
2. 실제 필요한 파일 목록 정리
3. 각 파일의 역할 설명
4. 다운로드 후 어떤 파일부터 열어야 하는지 결정
5. Python 환경에서 데이터를 읽는 코드 작성
6. train/validation/test 구조 확인
7. 샘플 몇 개를 직접 확인
8. 질환 label과 evidence 구조 확인
9. 데이터 통계를 출력하는 코드 작성
10. 이후 부분 관찰 실험을 어떻게 만들지 설계

**코드는 초보자가 따라갈 수 있게 단계별로 작성하고, 한 번에 거대한 코드를 만들지 말 것.**

각 단계마다:

**무엇을 하는지 → 왜 필요한지 → 코드 → 예상 결과 → 다음 단계**

순서로 설명해줘.

이제부터 이 내용을 MedMap 프로젝트의 기준으로 삼고 실제 프로젝트 작업을 시작하자.
